## 组件不够


## 布局问题

- **P-07**(需求 judge,1 页):同一条问题的对比度数值在问题清单和修复建议表里互相矛盾(一处写下降后的值、另一处写调整前后相同),读者不知道以哪个为准,也无法判断这次修改是否真的解决了问题。
  - 赢的做法:同一条问题的基线值和目标值在问题清单、修复动作、明细各处一致,并在同一编号下给出改前改后数值。
  - 证据:c4: 「下一步」的 P5 一行标题写「对比度下降到 2.6」,右侧标签却写 #FFFFFF → #FFFFFF、5.00 → 5.00,同一行两个数字对不上,读者不知道以哪个为准;c4: 修复动作表写 5.00 → 5.00,对比度明细写 2.52,两处数值不一致且都没有说明口径,读者来回核对仍无法判断主按钮悬停有没有修好
- **P-08**(需求 judge,4 页):对比度、色差等检测明细表只按位置名或颜色对列行、不带问题编号,位置写法还与问题清单不一致,读者无法把某一行数值直接对到某条问题,只能按文字来回配对,容易配错或漏看。
  - 赢的做法:修复动作表和「下一步」都以问题编号为主键列出对应数值,检测明细的每一行也标出所属问题编号、位置写法与问题清单统一,读者不必按文字配对。
  - 证据:c1: 「混淆色」表仍只按「位置 + 颜色对」列行、没有编号列,读者要拿「折线图系列 2 和 3」这类文字回「明细」表逐行比对,才能知道它属于 P1 还是 P6;c2: 对比度检查表只写位置名「顶部白色标题」、不带 P2 编号,而问题清单里同一处写「顶部标题」,读者要来回配对才能确认对应哪条;c3: 文字对比度表和颜色混淆明细表不带 P 编号,读者要在三处之间按位置文字和色值来回找,才能把 P1、P2 落到具体行;c4: 18 行对比度明细只列文字/背景名,不带问题编号,读者要拿着「辅助文字/区块背景」这些名字回问题清单逐条比对
- **P-09**(需求 judge,1 页):修复动作表里有些改动行匹配不到问题编号(显示「—」),问题清单里也没有对应条目,读者无法判断这些改动覆盖了哪条问题、还是有问题漏了修复。
  - 赢的做法:修复动作表的每一行都能落到一个问题编号,匹配不到的改动在问题清单里也有对应条目,读者不会误判漏项。
  - 证据:c4: 「成功文字」「错误文字」两条修复动作的问题编号写「—」,问题清单里也没有以它们为主题的条目,读者只能猜它们是否属于 P2;c4: 读者要确认这两条颜色改动是否已列入整改,既看不到对应问题编号,也无从判断被略去是「不需要做」还是「漏了写」
- **P-10**(需求 judge,1 页):问题清单的建议列和「下一步」只给文字描述或改前数值,缺少修复后的目标值(改后数值),读者无法判断每条问题改成什么值才算改到位。
  - 赢的做法:每条问题在同一编号下直接给出改前与改后的数值(目标色值与达标对比度),读者一眼能判断改成什么值才算到位。
  - 证据:c3: 全篇只有改前数值(对比度 2.22、各组 ΔE)和目标描述(加描边、改偏橙的黄),没有修复后的目标值或「改后」列,读者无法判断是否改到位;c3: 问题清单的「建议」列只写「缓行改为偏橙的黄」这类文字、不给目标色值,读者还得自己定方案再回头核对
- **P-11**(需求 judge,1 页):问题清单的「影响」列用色觉类型缩写、表头还被页面边缘截断,与「按色盲类型」里的全称对不上,读者无法就地确认每条问题影响哪些色觉类型。
  - 赢的做法:「影响」列直接写色觉类型全称(红色盲、绿色盲、蓝色盲),表头完整显示,读者不用对照缩写或回看上文。
  - 证据:c3: 该列只用「红/绿/蓝」缩写且表头被页面右边缘截成「影响(红/绿/:」,读者无法就地确认缩写含义,要回看上方图表;c3: 缩写与「按色盲类型」里的「红色盲/绿色盲/蓝色盲」全称不一致,读者需自行判断两者指同一件事

## 已解决

- **P-01**(需求 judge):每条问题与其修复动作分散在不同节里,编号体系也对不上,清单本身只有严重度标签和一句话描述,读者无法把某条问题直接对到它的修改动作,还可能漏掉最严重的那条。
- **P-02**(需求 judge):混淆色的色差数值被拆在柱状图和明细表两处,图例与表格的色型顺序还不一致,读者要上下反复对照才能确定某个 ΔE 属于哪对颜色、哪类色觉。
- **P-03**(需求 judge):按色觉类型查看问题数量或受影响情况时,这些信息没有直接落在核心指标或问题清单里,读者要把总数拆到类型必须往下翻一节再回来对照。
- **P-04**(需求 judge):色觉模拟部分与结论、色差数据分处不同节,也没有覆盖受影响最严重的色觉类型,读者无法从模拟图直接验证结论,只能靠旁边的数字推断。
- **P-05**(需求 judge):「下一步」列出的整改项只覆盖部分问题、没有说明筛选口径,编号又与问题清单不是同一套,读者按编号逐条核对时会漏项,以为剩下的问题不需要处理。
- **P-06**(需求 judge):修复动作表(颜色调整、修复建议)和对比度、混淆色明细表只按位置或颜色名列行、不带问题编号,部分问题的修复值或改前改后数值也缺失,读者要按文字在两处之间来回配对,才能确认某条问题改哪个值、有没有改到位。

## 试过的改法

每个候选改了一条规则后,训练页上的效果;没采用的也留着,下次改规则先看这里。

- **c1**(需求 judge,规则 G1,采用):把问题清单扩成含「类型/位置/影响/严重度/建议」并按严重度高→中→低排序的明细表,同时让「下一步」改用同一套 P 编号、只取高严重度项(至少 3 条),以求每条问题能直接对到修复动作。依据 P-01。
  - 解决了:P-01;没解决:P-01
  - 带出的新问题:为了让「下一步」只放高严重度项,代码把条目 slice 到 max(3, 高严重度条数),当高严重度正好 3 条时中低严重度问题一条都进不了「下一步」(c1/c3/c4),读者会以为待办只有 3 条而漏掉其余;另外 c3 的 7 列问题表把最左「问题」和最右「建议」被中间列隔开、「影响」列文字折行,逐行横向对照反而比原来费劲。
  - 经验:方向对:把建议并入问题清单、清单与「下一步」共用一套编号,确实让「问题→动作」一眼对上,继续沿这个方向改;但要补两点——「下一步」别机械截断成 3 条,要么列全部问题、要么明写「仅列最严重 N 条,其余见明细」,别让读者当成待办全集;同时让「明细」里的建议能指到具体改动行(给颜色调整/修复建议表加 P 编号或改前改后数值),否则问题与具体改法仍要在两张表之间来回对。表宽要控制在「问题」与「建议」相邻或缩写影响列,避免折行后横向比较变难。
- **c2**(需求 judge,规则 G1,采用):G1 这次把问题清单的严重度提前、建议紧跟问题、影响缩为单字放末尾，新增紧贴问题清单、带问题编号和改前/改后数值的「修复动作」表，并让「下一步」去掉自带序号、按问题清单同一顺序逐条全列且内联改前改后数值。依据 P-05、P-06。
  - 解决了:P-05;没解决:P-06、P-07
  - 带出的新问题:「影响」列改用单字缩写、表头写「影响(红/绿/蓝)」后，c2、c3 的表头被页面右边缘截断，缩写与「按色盲类型」一节的全称对不上，读者要回看上方图表才能确认指哪种色盲——这是改动里「影响缩写并放末尾、表头改写」造成的。;新增的修复动作表靠位置文字反查问题编号，匹配不到就写「—」（c4「成功文字」「错误文字」两行），或只列出部分行又不说明筛选口径（c2 全表只有 P2 一行），读者会以为其余问题没有修复动作——这是改动里「问题编号取 where 与 location/title/suggestion 含相同文字、匹配不到写「—」」造成的。
  - 经验:方向是对的：问题清单与修复动作共用一套编号、修复表带改前改后数值、「下一步」不截断不另起序号，使 P-05 在四页都由没解决/部分解决变为解决，P-06 也由没解决推进到部分解决（c1、c2 解决，c3、c4 仍在），但 P-07 的数值矛盾（5.00→5.00 对 2.6/2.52）仍在。下次在此改法上补：给对比度、混淆色等明细表也加同一套问题编号列并统一各处位置写法，匹配不到编号的行不要写「—」而要注明归属或补条目；同时去掉「影响」单字缩写、避免表头被截断（写回「红色盲/绿色盲/蓝色盲」），并把「下一步」的数值 meta 与所属条目贴紧，避免被读成上一条的值。
