# ui-rl:输出层强化学习环境(重建计划)

ui-loop 的问题和改法见对话总结,这里只写怎么做。目标:**先得到一个在 loop 实际判断上准、稳的 reward,再用 Training-Free GRPO 的方式学习**。

代码、数据、组件库和生成 Agent 都在这个文件夹,运行时不依赖别的目录;ui-loop 原样保留,作对照。全部是 mock 数据,密钥只走环境变量。

## 2. 第 0 阶段:测基线(先做,不跑 loop)

| 步骤 | 做什么 | 产物 |
|---|---|---|
| 0.1 logprobs 探针 | 对 openone 的 `deepseek-v4.1-flash` 发一次带图的请求:思考模式 high,`logprobs: true, top_logprobs: 20`,要求最后输出一个 1–9 的数字;流式和非流式都试。再试官方 DeepSeek 端点。拿不到就记下来,R2 改用采样近似 | `runs/probe/` + README 里一句结论 |
| 0.2 抽页面对 | 真实 12 个候选(flow c1–c12)× 6 份样本,每对是「候选页 vs 它的基线页」,共 72 对;另加 A/A 对测 judge 噪声:ui-loop 每次换版本都按同一指南再生成一遍训练页(`traces/*-twin`),twin 页 vs 对应的当前页,取 12 对。cvd 的候选以后可以照样加 | `labels/pairs.json` |
| 0.3 盲标 | `label.html`:左右随机交换,只给页面不给版本名;选 A 明显好 / A 稍好 / 差不多 / B 稍好 / B 明显好,可写一句理由;结果存本地并能导出 JSON。一周后随机重标 20 对 | `labels/human.json` |
| 0.4 现在的 judge 重复判 | rubric31 原判法,每对两种顺序 × 5 遍 | `runs/baseline-judge/` |
| 0.5 打分 | `eval-reward.mjs`:一致率(判出的对里和人工一致)、覆盖率(判出的比例)、复测一致(同一对多次判定一致)、A/A 对上的误判率;人工自己前后一致率 | `runs/baseline-judge/report.md` |

**这一阶段回答一个问题:现在的 judge 在 loop 的实际判断上到底准不准、稳不稳。** 人工前后一致率是 reward 能达到的上限。

## 3. 第 1 阶段:新 reward

三层,按顺序判,前一层不过就不往下走。

### 3.1 第 1 层:硬约束

直接用 `shoot.mjs` 的程序检查。有任何问题的页面在组内排最后,不参加比较。

### 3.2 第 2 层:量化指标(`lib/metrics.mjs`)

在渲染时从 DOM 量,每页输出一组数。先做这几项,每项都要在标注集上看和人工判断的方向是否一致,不一致的去掉:

| 指标 | 对应 rubric | 量法 |
|---|---|---|
| 节间距 / 节内间距 | 2 分组和韵律 | 相邻 section 的间距中位数 ÷ section 内相邻块间距中位数,≥ 2 为好 |
| 间距落在刻度上的比例 | 1、7 | 所有块间距落在 design.md 刻度(4 的倍数等)上的比例 |
| 左边线数 | 7 网格对齐 | 内容块左边缘 x 坐标聚类后的簇数,越少越整齐 |
| 字号级数 | 4 字体层级 | 页面上出现的不同字号数 |
| 强调色种数 | 5 色彩统一 | 非灰色文字和填充色的种数 |
| 同类组件高度差 | 6 同类一致 | 同一行同类组件高度的极差 |
| 最空一屏的留白比例 | 1 留白 | 每 900px 一屏,内容面积占比的最小值 |

用法:作为组内排序的一个约束。指标明显更差(超过阈值)的页面,不能排在明显更好的页面前面;差别在阈值内的交给第 3 层。

### 3.3 第 3 层:有刻度的两两比较(`lib/judge.mjs`)

- 输入:同一份数据的两页。整页缩略图 + **按节裁出的对照图**:同名的节左右并排,两页都有的节才比;只出现在一页的节单独列出。
- 输出:7 条标准各给一个 1–9 的数(1 = A 明显更好,5 = 差不多,9 = B 明显更好),最后一个总体数。要求每个数单独占一个 token。
- 期望:读每个数字位置的 top_logprobs,只留 1–9,归一化后求期望 E,p = (E − 1) / 8 是「B 更好」的概率。
- 两种顺序:p = (p(A,B) + 1 − p(B,A)) / 2。
- 汇总:7 条的 p 和总体 p 都存;排序先用总体 p,7 条用于提炼经验和分析。
- 拿不到 logprobs 时:同一请求采样 k = 5 次,用 1–9 的频率当分布。
- 模型:先用 `deepseek-v4.1-flash`;第 1 阶段末再用同一标注集试一个不同家族的多模态模型(需要另一个 key),准的那个留下。

### 3.4 验收

在第 0 阶段的标注集上跑 `eval-reward.mjs`,和基线并排比:

- 判出的对里和人工一致 ≥ 85%
- 覆盖率 ≥ 60%(|p − 0.5| 超过阈值才算判出,阈值在标注集上选)
- 同一对重复判,判出方向一致 ≥ 90%
- A/A 对上判出的比例 ≤ 10%
- 画校准曲线:p 分 5 档,每档里人工认为 B 更好的比例

**达不到就停在这里改 reward,不进第 2 阶段。**

## 4. 第 2 阶段:数据

`data/gen-data.mjs`:

- 每个 Skill 扩到 24 份:原有 6 份 + 新生成 18 份。
- 生成方式:把 `make_data.py` 的结构写成 JSON schema;LLM 按 schema 写新样本,题材、产品数、步骤数、问题数、文字长短都要有差异(特别要有内容很少和很多的样本)。
- 程序校验:字段齐全、编号连续、KPI 和明细对得上;cvd 的对比度和色差照旧由程序算,不让模型写。
- 图:沿用 `make_images.mjs`、`simulate_cvd.py`,改成接受样本列表。
- 划分:train 12 / val 6 / test 6。test 只在最后用一次。
- 人工抽查 5 份,看数据像不像真的报告。

## 5. 第 3 阶段:训练(照 Training-Free GRPO)

照论文(arXiv 2510.08191)和官方代码(TencentCloudADP/youtu-agent 的 `utu/practice/`、`utu/prompts/practice/experience.yaml`)做。和论文不同的地方都列在 5.5,每处写了原因。

### 5.1 用词(全文只用这些)

| 词 | 意思 | ui-loop 里对应 |
|---|---|---|
| 报告数据 | 一份 JSON(加它引用的截图),生成 Agent 的输入 | 样本 |
| 数据特征 | 程序从报告数据算出的几项:产品数、每个产品的步骤数、有备注的步骤比例、有没有阶段对比和共性做法、问题数 | — |
| 页面 | 生成 Agent 根据一份报告数据写出的一版 Page.tsx 和截图 | 页面 |
| 输出指南 | `g0.md`,人写的,训练中不改 | 输出指南 |
| 经验清单 | 训练改的东西:编号的短句,接在输出指南后面一起放进生成 Agent 的系统提示词 | 输出指南里的规则 |
| 模式清单 | Maintainer 维护的成功模式、失败模式,每条带出处,一直累积;不给生成 Agent 看 | 问题清单 |
| 修改记录 | Recorder 写的:经验清单每次改了什么、依据哪些模式、之后的效果 | 修改记录 |
| 一步 | 一份报告数据:生成 6 版页面、打分、Maintainer、Reviser、Recorder | 一轮 |
| 一遍 | 训练用的报告数据每份都走过一步 | — |

### 5.2 一步

1. **生成**:生成 Agent(`gen/scripts/generate.mjs`,从 ui-loop 复制)拿「设计规范 + 组件说明 + 输出指南 + 当前经验清单」,从零写 6 版页面,6 版同时跑。经验清单这样接在输出指南后面:「## 经验(写页面前先读;和上面的规则冲突时以经验为准)」加编号列表。
   - 不设温度:生成用 DeepSeek 思考模式,温度参数不起作用。同一份指南生成的几版本来就有差别:第 0 阶段 12 对 A/A 页面(同一份指南生成两次),人工判出高下的 10 对。
   - 一版超过 20 分钟没写完,或构建失败没有截图,就丢掉重新生成,最多 2 次(以前的记录里中位数 4–7 分钟,最慢一次 74 分钟)。还是不行就这一步只用剩下的版本。
2. **打分**:judge(ia5)把 6 版两两比较,15 对,每对两种顺序,取平均得 v(-2..2)。每版的分 = 它在 5 对里的 v 之和(-10..10)。15 对的 |v| 都小于 0.5(一对都没判出高下),这一步只记录,不往下走。
   - 可信度:ia4v(ia5 的前一版,只差结构)在 A/A 页面上和人工一致 9/12。所以单对比较大约四分之一会判反,靠 5.2 第 4 步的「至少 2 份报告数据」和修改记录来抵消。
3. **Maintainer**(LLM,文字,不看图):
   - 每版各调一次:输入报告数据、数据特征、这版的 Page.tsx、分数、judge 在 5 对比较里对这版的评语、当前经验清单。输出:这版的排版决定(节的顺序、每节用什么组件、备注和截图怎么放……)、judge 怎么评它、它照了经验清单里的哪几条。
   - 6 版放在一起调一次:输入 6 版的总结和分数。输出:高分的好在哪(成功模式)、低分的差在哪(失败模式),每条写清楚是什么排版决定。
   - 更新模式清单(`runs/<run>/patterns.json`,渲染成 `patterns.md`),调一次:已有的模式补出处,新的加一条,意思相同的合并。每条出处记:哪份报告数据、它的数据特征、第几版、分数、judge 评语。失败模式分「布局问题」和「组件不够」;组件不够的只记进 `runs/<run>/triage.md`,训练中不改组件库,结束后交给组件 Agent 或你。
4. **Reviser**(LLM,调一次,对应论文的单组更新):
   - 先读修改记录:效果是「失败」的经验,这一步修改或删除;删掉的经验,模式清单里没有新出处就不再加回来。
   - 再读整份模式清单和输出指南:只用**至少在 2 份报告数据里出现过**的布局模式(程序先筛出来给它)。对照当前经验清单,决定新增 / 修改 / 删除 / 不动。
   - 每条经验写成「当〈条件〉时,〈做法〉」,条件只能用数据特征里有的项;不超过 40 字;注明依据哪几条模式。和输出指南冲突的,注明冲突的是哪条。
   - 输出的操作由程序执行,得到新的经验清单(`runs/<run>/lists/s<N>.md`,每一步存一份)。
5. **Recorder**(程序,不调 LLM):写修改记录(`runs/<run>/record.json`,渲染成 `record.md`):
   - 这一步每处改动:改前、改后、依据的模式、和输出指南冲突的标出来。
   - 之前每条经验的效果:用第 3 步 Maintainer 标的「照了哪几条」,这一步里照这条做的页面和没照做的页面,平均分谁高。累计到两边各至少 3 版时下结论:照做的平均分高 1 以上 = 有效,低 1 以上 = 失败,其余 = 看不出。经验进了清单以后大多数页面都会照做,很多经验会一直是「看不出」,这是正常的。
   - 下一步的 Reviser 第一件事读它;你也看它了解每条经验怎么来的、有没有用。

### 5.3 每一遍结束:验证用报告数据上观察

- 4 份验证用报告数据,「输出指南 + 当前经验清单」和「只有输出指南」各生成 2 版,交叉比较(每份 4 对,两种顺序)。记下每份上有经验清单的一边赢、输还是平。
- 只记录,不回滚(论文的评测也只观察)。最终用哪一遍的经验清单,看完记录由你定。

### 5.4 试点

- 只做交互流程。训练用 8 份:原有 f1–f4 + 新写的小、中、中、大各 1 份;验证用 4 份、测试用 6 份都是新写的,也各档都有。
- 跑 2 遍,每遍打乱顺序,共 16 步。第 1 步经验清单是空的;最早到第 2 步才可能有经验写进去(要 2 份报告数据)。
- 量:每步生成 6 版(约 10–15 分钟,等最慢一版),judge 30 次,Maintainer 8 次、Reviser 1 次 LLM 调用,约 15–20 分钟;16 步约 4–5 小时。每遍结束的验证 16 版、32 次比较,约 20 分钟。
- 你要做的:开始前抽查 5 份报告数据(第 2 阶段);结束后盲标验证用的 4 对(有经验清单 vs 只有输出指南,每份 1 对),看经验清单、模式清单、修改记录、triage.md。judge 和你的判断对不上,先查 judge,不往下扩。
- 试点看得出提升,再扩到训练 12 份、两类报告。

### 5.5 和论文不同的地方

| 论文 | 我们 | 原因 |
|---|---|---|
| 和标准答案比,对 1 错 0 | judge 组内两两比较,每版的分是 v 之和 | 页面没有标准答案;论文也做了不用答案、只靠组内比较的版本,仍然有效 |
| 100 份,每 50 份改一次经验清单 | 8 份,每份改一次 | 数据少,攒一批再改,一共改不了几次 |
| 每题 5 个回答,温度 0.7 | 每份 6 版,不设温度 | 6 版是你定的;生成用思考模式,温度不起作用 |
| 组内对比写完经验就丢 | Maintainer 把成功、失败模式累积成模式清单 | 每步只有一份报告数据,要靠累积的模式看出哪些做法反复有效 |
| LLM 自己决定新增哪条 | 只用至少 2 份报告数据里出现过的模式 | 论文的分数是准的;我们的 judge 单对比较约四分之一判反,只出现一次的模式可能是判错来的 |
| 只记录,不判断效果 | Recorder 算每条经验的效果,Reviser 先读 | 和 ui-loop 一样,失败的做法不再试 |
| 经验条件由 LLM 写 | 条件只能用程序算的数据特征 | 免得写出数据里没有的条件 |
| 没有整批合并以外的规定 | 不变 | — |

## 6. 第 4 阶段:最终评测

- 测试用报告数据 6 份,「输出指南 + 最终经验清单」和「只有输出指南」各生成 2 版,你盲排。指标是你认为前者更好的比例。

- 输出指南(guides/g0.md)和经验清单的关系:试点先「输出指南不动 + 经验清单」;经验清单里一直有效的经验,由你决定要不要并进输出指南。
- 生成模型的上限:试点看不出提升时,先换一个更强的生成模型做一次对照,判断是模型能力问题还是方法问题。
